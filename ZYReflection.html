Zi Yang's Reflection on Basic Agentic SE

This document records key insights I got from the journey of building EvidenceLogger. It includes prompts, suggestions, and lessons learned throughout its development.

1. What tasks was Codex customized to perform, and how was the appropriate skill set determined?

The agent was customized for several recurring EvidenceLogger tasks:

  • Implementing custody-state transitions with authorization, atomic audit logging, and rollback behavior.
  • Modifying SQLite migrations, JDBC repositories, row mappings, constraints, and transactions.
  • Selecting behavioral tests at the domain, service, persistence, presentation, or acceptance level.
  • Wiring application startup, authentication, role routing, logout, and resource shutdown.
  • Performing specification-based code reviews and scoped SOLID/DRY refactoring.
  • Producing user and developer documentation based on current implementation evidence.

The appropriate skills were determined from the task’s affected boundary and risks. For example, a custody workflow change used custody-transition; a repository or migration change added sqlite-persistence-change; behavior changes used behavioral-test-design; and startup or role-routing work used application-composition. Documentation and refactoring used their dedicated skills.

But most of the time, these skills were automatically triggered via the Iterative TDD workflow. This skill scopes the tasks I wanted Codex to perform, and performs the tasks according to a pre-determined plan, so I can track what the agent is doing for each iteration of code change.

The skill descriptions included both trigger conditions and exclusions. This helped prevent a persistence skill from inventing business rules, a composition skill from implementing missing features, or a code review from silently changing production code. When tasks crossed boundaries, the smallest relevant combination of skills was used rather than one general-purpose workflow.

2. How did you define a specific skill and make sure it was working?

1. Iterative TDD skill

I created this skill following my experience from MP1. It was initially defined with reference to the workflow I used in MP1 as follows:

  1. Create a checklist for the task in a .gitignore-d folder that the agent can read.
  2. Decide the next natural stand-alone increment that moves the code closer to the target. Follow the checklist created in step 1 closely. If a bullet has not completed, continue working on it before moving to the next bullet in the checklist.
  3. Implement that increment.
  4. Test it to ensure there are no regressions, using the JUnit tests and checkstyle tests.
  5. Commit the changes with a detailed commit message.
  6. Generate a visual diff using the $present-changes-visually skill. Also explain the rationale for the change and its pros and cons.
  7. If an iteration in the iteration checklist is completed in this iteration, check the box of the item in the checklist.
  8. Briefly outline the next increment to be done in the next iteration. If there are no more increments worth doing, say so and stop.
  9. Go ahead and do the first iteration.

The skill was checked in three ways:

  1. The grader passed when ran.
  2. The items in the checklist are completed.
  3. The visual-diff generated correctly reflects the changes I intended the agent to make.

This was more useful than checking only that the skill file was syntactically valid. The tests demonstrated that the skill works as intended and modifies code according to my intentions.

2. Code Refactor skill

I realised that many times when using a "not-so-capable" model (e.g. Luna), the code generated was not as "clean" and concise as code generated by "more advanced" models (e.g. Sol). But the credits usage for more advanced models was significantly higher (depleted by 5-hour usage limit quickly). So I decided to create a skill to refactor the code the generated by less advanced models, but still using the less advanced model to execute the skill. From observation, this allowed me to save much more credits, and allowed me to better understand the code. But this was of course done at the expense of time, because I spent much more time refactoring than generating more code to build actual product logic.

I defined some common SE principles in the SKILL.md file, such as SOLID, DRY and KISS. I then asked the agent to suggest more principles related to improving cohesion and reducing coupling, because I realised that less advanced models tend to complicate logic very quickly by adding more code that is less readable.

3. Code Review skill

Rather than asking other people to review, I asked the agent to review its own code, and got it to improve itself using the iterative TDD skill. This made reviewing code less painful for other people, and also saves time for both my teammate and I.

3. What tasks were handled effectively?

The agent was especially effective at narrow, well-specified backend and testing tasks.

For persistence work, real-SQLite tests verified row mappings, deterministic ordering, conditional transitions, uniqueness constraints, and typed conflicts. This provided stronger evidence than mocked repository tests.

The agent also improved code quality through scoped refactoring (using the code-refactor skill). It replaced repeated 17-field positional audit-event construction with named factories. It also separated transaction-aware authorization from workflow orchestration, and split large workflow responsibilities while preserving behavior. Existing tests caught compatibility issues during these changes.

Code-review work (using code-review skill) also produced useful results. Reviews found persistence, authorization, migration, error-handling, and transaction risks, after which focused regression tests were added. One review identified nine valid issues, while another identified six additional specification-aligned findings.

Documentation work was very effective. Re-reviewing the application exposed completed Custodian workflows and a changed Investigator date format that stale documentation did not yet reflect. See the User Guide re-audit log.

Overall, the greatest productivity improvements came from automating repetitive repository inspection, implementing routine workflow layers, generating focused regression tests, and running consistent verification after each logical change.

4. Where did the agent require guidance or correction?

Firstly, Codex required additional guidance when requirements were ambiguous or mainly visual.

A significant correction occurred when I clarified that returned evidence must enter HANDIN_AWAITING_ACK before inspection. The earlier implementation had followed an incomplete interpretation of the transition table. Luckily, the correction was caught before later work, but a stronger state-diagram reconciliation step would have prevented the rework. See the state-correction log.

I also had to clarify that removing “hold” meant removing the complete behavior, not merely renaming or deleting one state. This shows that apparently small terminology changes can affect DTOs, validation, audit events, tests, and specifications.

All in all, the lesson learnt here is that being more specific in the requirements for Codex will definitely smoothen the implementation process.

Also, UI work required more correction. Codex could inspect code and run controller tests, but visual inspection was unavailable. Similarly, the Investigator workspace task was rated low because the process was slow, so probably more precise UI requirements would have helped.

The agent definitely did not cause regressions, but a lot of time was spent defining requirements and refining the UI.

5. What would I change next time, and what additional skills or tools would help?

I would probably make the following changes:

  • Add an EvidenceLogger-specific UI and visual-QA skill covering JavaFX layout inspection, accessibility, consistent styling, and screenshot comparison (though I'm not sure how capable Codex is to do this).
  • Re-audit user documentation immediately after each role-workspace change instead of waiting for a later documentation pass (maybe include it in the iterative workflow)
  • Maybe add a very detailed plan/specification about the product before it is even built. This can be discussed with the agent and use k-shots prompting or tree-of-thoughts strategy to brainstorm alternative specifications too.

I would retain the narrow testing and review skills because from the many iterations, there are many examples where explicit scopes and exclusions worked well.

6. What did you learn about designing an effective single AI agent?

An effective single agent should not be designed using general guidelines. Personally, I feel the more specific we are with our requirements, the better the agent's decision, because it will narrow down the possibilities for the agent, allowing the agent to fully comply with what I intended. It may also help to define a "playbooks" for the agent (in AGENTS.md), where each "playbook" should state:

  • Which specifications and code must be inspected.
  • Which decisions the agent may make when implementing certain features.
  • Which ambiguities require human input.
  • What observable behavior must be tested.
  • What verification must be run before completion.
  • What evidence must appear in the final report.

Also, I personally feel that different software engineers may prefer different workflows, so it helps to have a private AGENTS.md which defines how I want to work. I defined my own AGENTS.md in my local .codex/ directory, and intentionally excluded it from git, so that I can define more non-project specific workflows and tools to work with.

Finally, I think human oversight remains important for product interpretation and visual judgment. It feels like most of the work being done by hand in this project is specifying the requirements of the product (to the finest detail) and testing. This makes me feel like I have control over the agent, and that the agent does not implement everything too fast such that I lose track of the logic of the code. This effective division of responsibility allowed me to work faster, while thinking deeper into the specifications and architectural decisions of the product.
