Gabriel's Reflection

1. What tasks was the agent customized to perform, and how did I choose the skills?

These were the five skills I made:

  • application-composition for connecting existing repositories, services, sessions, role views, startup, logout, and shutdown.
  • behavioral-test-design for deciding what kind of test would best prove that a feature works.
  • custody-transition for changes to checkout and evidence-custody states, including authorization, audit logging, and rollback when something fails.
  • evidence-backed-documentation for writing guides based on the current code and actual test results instead of plans or assumptions.
  • sqlite-persistence-change for migrations, JDBC repositories, database constraints, row mappings, and transactions.

I chose the skills by looking at the main risk of each task. For example, a migration needed sqlite-persistence-change, connecting that repository to the rest of the running application needed application-composition, etc.

2. How did I define a specific skill and make sure it was working?

I will use behavioral-test-design as an example. The first step was to identify the problem I wanted the skill to solve. Simply asking the agent to "add tests" was too vague. The agent could add many tests without checking the behavior that was actually at risk. It could also test private implementation details, making the tests difficult to maintain when the code was refactored.

I therefore made the agent describe what needed to be proved before writing a test. This included the user or role performing the action, the input, the starting state, the expected result, the audit record, and anything that must remain unchanged. The skill then had to choose the smallest test level that could prove the behavior:

  • a unit test for a rule contained within one domain object;
  • a direct service test for authorization and role checks;
  • a test with a real temporary SQLite database for queries, constraints, and rollback;
  • a presentation test for controller and view behavior; or
  • a larger acceptance test only when the workflow crossed several parts of the application.

I also added instructions about what the skill should not do. It could not treat a high coverage percentage as proof that the application was correct, test private methods, use a shared developer database, add a new testing dependency without approval, or change production behavior only to make a test easier to write.

I checked the skill in several stages. First, the skill validator confirmed that the file structure and metadata were valid. Second, I gave it two example tasks to see whether it chose an appropriate test. For a wrong-role service call, it selected a direct service test using small fake dependencies. For a partial database-write risk, it selected a real-SQLite test using the actual transaction runner and a deliberately failing audit writer. These were useful manual forward tests because they checked whether the instructions guided the agent toward the expected approach. This is recorded in the behavioral-test skill creation log.

The stronger evidence came from using the skill on real project work. During the A7 testing task, the agent added tests for migrations, rollback, authentication, authorization, assignment isolation, and Custodian workflows. The final check ran 180 tests with no failures or skipped tests. One of the new tests initially used an assertion that searched too broadly, and the test run exposed this problem. The agent corrected the fixture and assertion instead of weakening the expected application behavior. See the A7 test log.

However, a valid skill file and passing application tests do not automatically prove that the skill itself works well. My checks mainly covered individual example scenarios and the final application result. I did not systematically test whether each skill triggered for the right prompts, avoided unrelated prompts, followed every required step, or continued to work when combined with other skills.

The original creation of custody-transition had the weakest testing evidence. It passed the validator and repository checks, and later tasks showed that it could help with checkout persistence and rollback, but it was not tested with a focused example when it was created. Therefore, I can say that later tasks gave me some confidence in the skill, but I cannot claim that I tested its trigger behavior or instructions thoroughly.

3. What tasks did the agent handle effectively?

The agent was definitely most effective on backend tasks where the expected behavior and failure conditions are described clearly.

One good example was the database and authentication infrastructure. Using sqlite-persistence-change and application-composition, the agent added the database connection setup, migrations, transaction handling, authentication, sessions, authorization, audit storage, and startup wiring. Four focused groups of integration tests passed, followed by a full check with 24 tests and no failures. The agent also noticed that the role-specific screens did not exist yet and did not create fake screens or unfinished replacements just to make the application appear complete. See the database and authentication log.

The persistence skill was also useful when work from two developers was merged. The agent found that the checkout SQL did not match the first database migration. It kept the confirmed HANDIN_AWAITING_ACK state, left the existing migration unchanged, and added a new V002 migration to update the database safely. The final check passed with 41 tests. This saved time because the agent compared the specification, SQL, repositories, and tests together instead of treating the problem as only a compilation error. See the checkout persistence reconciliation log.

The testing skill improved code quality when code-review findings were fixed. For example, the agent added regression tests for the user session changing while an audit record was being created, and for database cleanup failing after a transaction had already committed successfully. These tests checked the result visible through the public service and the final database state instead of checking private method calls. This gave me more confidence that the fixes addressed the actual bugs.

evidence-backed-documentation was effective because it made the agent separate three different things: what the specification required, what the code currently implemented, and what had actually been tested. When writing the Developer Guide, it checked the Gradle tasks, data paths, migrations, logging, tests, and packaged JAR. It ran 186 tests, generated coverage reports, and passed the release smoke test. It also clearly stated that MarkBind, macOS, Linux, and interactive JavaFX behavior had not been verified instead of assuming that they worked. See the Developer Guide log.

Overall, the main productivity gain came from letting the agent inspect related files, make a focused change, and run the relevant tests after each step. The skills also improved testing efficiency because they guided the agent toward the type of test that could expose the real problem, especially when the behavior depended on SQLite rather than only Java code.

4. Where did the agent require guidance or create additional work?

The largest weakness was definitely visual UI work. Automated presentation tests could confirm that a control existed or that a style was applied, but they could not confirm that the interface looked correct in a real JavaFX window. I had to report that the login form was off-center and that the error message used the wrong color. I also had to provide screenshots showing incorrect ComboBox highlighting and insufficient spacing. The agent fixed these issues after receiving the visual feedback, but details such as popup behavior, hover colors, sizing, and spacing still required a human to inspect the application. See the login correction log and dropdown correction log.

The automated tests were still useful for preventing known problems from returning, but they were not a replacement for visual judgment. In this area, the agent reduced the time needed to write the code, but I still had to spend time checking and explaining what looked wrong.

The agent also needed a clear human decision when a request could change a business rule. During the Custodian redesign, voiding evidence was not only a UI action. It required a new terminal state, a new audit event, authorization rules, a migration, and changes to search results. I had to approve this behavior before the agent implemented it. This was the correct place for human guidance because the skills should follow confirmed rules rather than decide new product behavior on their own.

5. What would I change next time, and what other skills or tools would help?

I would make the following changes:

  • Add a more systematic way to test whether each skill triggers for the correct tasks and follows its instructions, instead of relying mainly on the success of the generated application code.
  • Add a JavaFX visual-testing workflow because the existing automated tests did not catch several layout, color, focus, and hover problems.
  • Use the documentation skill after major UI or workflow changes so that outdated instructions are corrected earlier.
  • Reduce unnecessary skill overlap by making the trigger descriptions more precise and requiring a clear reason for selecting each skill.
  • Prepare the testing tools and environment before development begins so that missing packages, Gradle cache permissions, and unavailable documentation tools do not interrupt verification.

I would keep the five skills separate. Combining them into one large EvidenceLogger skill might make it easier to invoke, but the instructions would become harder to follow and the agent would be more likely to make unrelated changes.

6. What did I learn about designing an effective single AI agent?

I learnt that an effective single agent needs both general project rules and smaller instructions for specific kinds of work. AGENTS.md provides the general safety, architecture, testing, and logging rules. The skills then tell the same agent how to handle a particular risk, such as a database migration or custody-state change. This is more useful than trying to create a different general-purpose agent for every task.

I also learnt that a skill should describe a working process instead of copying the product specification. The business rules should remain in specs/, and the agent should inspect the current code before making a change. A good skill tells the agent what evidence to read, which decisions it is allowed to make, when it must ask for help, what behavior it must test, and what results it must report.

I also learnt that human oversight should be designed into the workflow instead of added only when something goes wrong. In this project, approval before introducing the evidence-voiding rule was a useful decision point, while the final reviews and interaction logs made the work easier to inspect. The agent was most reliable when it was clear which decisions it could make independently and which decisions still belonged to me.

Most importantly, passing a skill validator is only the first level of evidence. Example tasks show whether the skill guides the agent toward the right approach, while real implementation logs show whether it remains useful during actual development. I also learnt that testing the generated application and testing the agent's workflow are not the same thing. Human review is still necessary for unclear product decisions, architecture, maintainability, and visual quality. The best division of work for me was to let the agent handle code that could be checked through specifications and tests, while I remained responsible for approval decisions and judging whether the application worked and looked right as a product.
